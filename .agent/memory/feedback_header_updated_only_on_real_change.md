ファイルの中身（コード本体）に変更が無いなら、42ヘッダの `Updated:` を現在時刻に書き換えて
コミットに含めるべきではない。「開いた・触れた」だけで日時を進めない。

**Why:** `Updated:` はそのファイルが実際に編集された時刻を表すもの。中身が変わっていないのに
書き換えると、コミット履歴上「変更した」という誤った記録になる。

**How to apply:**
- コミット対象を決めるときは、実際に diff がある（内容が変わった）ファイルだけに `Updated:` の
  書き換えを適用する。
- [[timed-git]] の作業（Created/Updated 修正、履歴の retime）でも、対象ファイルは必ず
  「このブランチのコミットで中身が変わったもの」に限定する。中身が変わっていないファイルは
  たとえ `Created`/`Updated` が古くても触らない。
- 逆に、中身が変わっているのに `Updated:` が古いまま残っているファイルは見つけ次第直す
  （このタスクで実際にやった: `git show <base>:<file>` と `git show HEAD:<file>` の9行目を比較して
  内容が変わっているのに Updated が同じなら stale と判定する手法）。
- stale 判定の対象ファイルは、手元で「たぶんこれとこれ」と手動列挙せず、必ず
  `git diff --name-only <base> HEAD`（や各コミットの `--name-status`）で機械的に全ファイルを
  洗い出してから判定する。手動列挙だと `Makefile` のような「コードと見なしていないファイル」を
  取りこぼす（実際に1回取りこぼして指摘された）。
- **`git filter-branch --tree-filter` は各コミットを履歴上の独立したスナップショットとして
  再構築する（親の書き換え結果を自動で前方伝播しない）**。あるコミットで `Updated` を直しても、
  同じファイルが変更されていない次のコミットでは元の値に「戻って見える」（実際にはその
  コミット自身の独立したオリジナルスナップショットが処理されているだけ）。
  - 1コミットだけ実際に内容が変わるファイルを直すときは、`$GIT_COMMIT` 条件を付けずに
    range全体へ無条件で `sed` を当ててよい——ただし**その実変更コミットが range の最初の
    コミットである場合に限る**（それより前に「変更前のまま存在する」コミットが range 内に
    無いこと）。
  - 実変更コミットが range の途中/最後にある場合（＝それより前に unchanged な状態で存在する
    コミットが range 内にある）は、無条件 sed だと「変更前のコミット」まで誤って書き換えて
    しまう。`$GIT_COMMIT` で実変更コミットを判定し、それ以降のコミットにも**同じ値**を
    明示的に適用する（前方への自動伝播は無いので、変更が及ぶ範囲すべてに同じ値を明示指定）。
  - 複数回にわたって別々の filter-branch を継ぎ足すと、この前方伝播の欠如でバケツリレー的に
    ズレが蓄積する。最終的には「各ファイル×各コミット」で本当に内容が変わった地点を機械的に
    洗い出し（`git show <c>:<f> | tail -n +12` の本文だけをコミット間で比較）、1回の
    filter-branch で全コミット×全対象ファイルの目標値を確定させてから当てるのが確実。
  - 検証は「ヘッダーが変わっている ⇔ 本文も変わっている」を全コミット×全ファイルで機械的に
    突き合わせる（`STILL-WRONG-BUMP` / `MISSED-STALE` の両方をゼロにする）まで繰り返す。
  - `sed` の副作用にも注意: 日付置換のために `s/ 2026/2026/` のような雑な追加 sed を挟むと、
    無関係な行（`Created:` 行など）の空白まで壊すことがある（実際に一度壊して80桁チェックで
    発覚した）。置換は対象行にできるだけ限定した正規表現で行う。
