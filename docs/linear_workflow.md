# ガンマ補正とリニアワークフロー

### 0. sRGBとは

sRGB は国際標準規格(IEC 61966-2-1)のカラースペース(色空間)。
パソコンのディスプレイ・デジタルカメラ・プリンターなど画像を扱う機器を
sRGB のカラースペースで統一することで、どの機器でも同じ色を表現できるようにする目的のもの。
一般的に画像ファイルも sRGB の情報で保存されている。

### 1. ガンマ(ディスプレイの応答特性)

入力値(ディスプレイに入力する値)と出力値(実際の光量)の関係を表す数値をガンマ(γ)と呼ぶ。

```
出力光量 = 入力値^γ
```

現代のディスプレイなどの機器は標準 2.2(2.0–2.4)のガンマ(応答特性)で設計されているため、
入力側があらかじめ逆のガンマ補正(約 1/2.2 乗)をかけておく必要がある。

```
ディスプレイへの入力 :  encoded = linear^(1/2.2)   ← ガンマ補正
ディスプレイの応答   :  出力光量 = encoded^2.2 = linear   ← 正しい光量で表示される
```

sRGB で保存された色情報はこのガンマ補正(約 1/2.2 乗)がかかっているため、
光量に対して非線形な値になっている(ガンマ 1.0 なら線形)。

### 2. ガンマ2.2の由来と利点

ガンマ 2.2 の由来はブラウン管(CRT)の電子銃の物理特性。
入力電圧に対する輝度がおよそ 2.2 乗の応答だったため、
入力側で逆補正をかける仕組みが最初からあった。

CRT が消えた現在もこれが規格として残っているのは、

- 過去の機器・コンテンツとの互換性
- 人間の目は暗部の変化に敏感なため、1/2.2 乗のエンコードによって
  8bit(256段階)の階調を暗部に厚く配分でき、バンディングを抑えられる

という利点があるため。偶然にも CRT の特性が人間の知覚特性とほぼ逆向きに一致していた。

### 3. sRGB伝達関数

sRGB の正確な変換は単純な 2.2 乗ではなく、0 付近を線形にした区分関数。

decode(sRGB → リニア):

```
linear = srgb / 12.92                       (srgb ≤ 0.04045)
linear = ((srgb + 0.055) / 1.055)^2.4       (srgb > 0.04045)
```

encode(リニア → sRGB):

```
srgb = 12.92 × linear                       (linear ≤ 0.0031308)
srgb = 1.055 × linear^(1/2.4) − 0.055       (linear > 0.0031308)
```

指数は 2.4 だが、線形部分と合わせた全体のカーブは `γ ≈ 2.2` に近い。
0 付近を線形にしているのは、べき乗カーブは原点で傾きが無限大(encode側)になり、
暗部の数値誤差・ノイズが増幅されるのを避けるため。

### 4. リニアワークフロー

非線形な値のまま線形な計算(加算・乗算・補間)をするのは誤り。
入力された色(sRGB)をそのまま足したりかけたりのライティング計算をして出力しても、
(中間色の)結果は正しくならない。

例: sRGB値 0.5 は物理的には約 21% の光量。
sRGB値のまま `0.5 + 0.5 = 1.0` とすると、
物理的には `21% + 21% = 42%` のはずが 100% として扱われてしまう。

そのため、ガンマ補正を一度取り除いて線形なもとの色情報に戻し、
計算してから、ガンマ補正をかけなおす。

```
入力(.rtの色・テクスチャ)      … sRGB(0–255・非線形)
  ↓ decode(ガンマ補正を取り除く)
ライティング計算・ブレンド        … リニア(float)
  ↓ encode(ガンマ補正をかけなおす)
出力(フレームバッファ)          … sRGB(0–255・非線形)
```

- decodeを忘れると、encode(1/2.4乗)とディスプレイの2.2乗が打ち消し合い、表示輝度がsRGB値そのものに近づく → 全体が白っぽく浮き、コントラストが失われる
- encodeを忘れると、リニア値にディスプレイの2.2乗が直接かかる → 中間調が沈み、全体が暗くなる

### 5. 量子化(float → 8bit)の丸め

encode の最後に float を 0–255 に量子化する。
単純な切り捨てではなく、「コード n と n+1 の境界」をリニア空間で持っておき、
境界と比較して近い方のコードへ丸めると、decode → encode で元の値に戻る
(ラウンドトリップが保証される)。

```
boundary[n] = decode((n + 0.5) / 255)

linear < boundary[n]  →  n
linear ≥ boundary[n]  →  n + 1
```

decode は 256 エントリのテーブル(LUT)参照で済む。
encode は逆引きテーブル(LUT)(または境界配列の二分探索)にすれば、毎変換の`pow` が不要になる。

逆引きテーブルの解像度は、1マスがコード(0-255)の境界を高々1つしか跨がない(`encoded[i+1] - encoded[i] <= 1`)粒度まで
細かくしておけば、テーブルで引いた候補コードに対して、boundaryを使った境界比較を1回行うだけで正確に丸められる(sRGB の場合は 4096 エントリで足りるが、任意のgammaに対してはテーブルサイズが爆発しうるので、256の固定長配列の二分探索で実装した)。
